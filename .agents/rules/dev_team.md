# Команда разработки — опциональный слой агентов

> Источник для: состава ролей и областей записи, ворот Arch / Dev / QA, коммитов, владения
> миграциями БД и статусом `in_dev`. Другие файлы на эти темы ссылаются сюда.
> Версия: 2026-11-12.

Опциональный слой: агенты `arch`, `ux`, `dev`, `qa`, `devops`. Он не входит в четвёрку
платформенных агентов (`analyst`, `orchestrator`, `worker_llm`, `worker_file`) и не меняет
их работу: без него платформа ведёт только аналитику. Платформо-независимые методологии
этих ролей — в `.agents/agents/` (`arch.md`, `ux.md`, `dev.md`, `qa.md`, `devops.md`);
экземпляры под конкретный проект (реальные каталоги кода, трекер, префикс задач) подключает
`python init_dev_team.py` из `templates/dev_team/`. Пока команда не подключена — её агентов
не вызывай.

## Роли и области — один писатель на область

| Агент | Задачи | Пишет только в |
|---|---|---|
| аналитик (ведущая сессия) | `Pre.RE-N` | `output/` (через MCP-инструменты), `product_docs/`, в том числе статус карточки БФ |
| `arch` | `Pre.Arch-N` | `architecture/`; блок «Архитектурное решение» страниц компонентов; задачи в трекере |
| `ux` | `Pre.UX-N` | `design/` |
| `dev` | `Pre.Dev-N` | код продукта (бэкенд, фронтенд, тесты к коду) и каталог миграций — только в задаче на изменение схемы |
| `qa` | `Pre.QA-N` | тесты продукта, `qa/` |
| `devops` | `Pre.DevOps-N` | compose-файлы, Dockerfile, `infra/`, `scripts/`, CI, `.env.example` |

- Параллельные задачи в одну область не заводятся. Агент сообщает, если смежная задача в
  работе, и не правит те же файлы.
- Пробел или противоречие в требованиях исполнитель не правит сам — заводит Issue или CR
  (5.4) аналитику.
- Формат названий задач и цикл по колонкам — `tasktracker.md`.

## Цепочка

```
Аналитик (требования, карточка БФ planned)
  → Arch (архитектура, декомпозиция на задачи)
  → UX (варианты) → [апрув владельца, Гейт 3]   — только для задач с изменением UI
  → Dev → QA
```

DevOps подключается по задачам окружения, сборки и деплоя. Задача с изменением интерфейса
идёт через `ux`; серверные и инфраструктурные задачи его пропускают. UI-цикл —
`ui_workflow.md`; общая схема и гейты владельца — `workflow_scheme.md`.

## Ворота

**Arch** берёт функцию в работу, только если выполнено всё:

1. карточка `product_docs/01_business_functions/BF-NN_*/README.md` в статусе `planned` с
   заполненным разделом «Планируемое изменение»;
2. требования, на которые она ссылается, утверждены (пакет утверждения 5.5);
3. аналитик подал сигнал в трекер: «аналитика по BF-NN завершена» со ссылками на карточку и
   пакет.

Проект без `product_docs/`: вход — утверждённые требования в `output/data/<project_id>/specs/`
и пакет 5.5.

**Dev и QA** берут задачу, только если:

1. карточка БФ в статусе `planned` или `in_dev`;
2. задача создана Arch и содержит вход, выход и критерии приёмки;
3. для задачи с изменением UI — есть `design/<задача>/decision.md` со статусом `approved`
   (`ui_workflow.md`).

Ворота не пройдены — назови, чего не хватает, верни задачу (Arch — аналитику, Dev/QA — Arch
или аналитику) и ничего не делай в чужой области. Если роль играет живой человек, правило то
же.

## Статус бизнес-функции `in_dev`

Карточку БФ пишет только аналитик, статус тоже. Arch при старте разработки (первая
подзадача Dev ушла в In Progress) пишет в эпик сигнал «разработка BF-NN начата»; аналитик
по этому сигналу переводит карточку в `in_dev`. Статусы и их смысл — `product_docs.md`.

## Миграции БД

Схему меняет Dev в отдельной задаче `Pre.Dev-N` на изменение схемы; Arch согласует
изменение схемы до реализации (комментарий в задаче или ADR). В других задачах Dev каталог
миграций не трогает: нужна новая колонка или таблица — запрашивает задачу на изменение
схемы. DevOps миграции не пишет, а применяет их при деплое (с предварительным дампом БД).

## Коммиты

- Dev, QA, DevOps и UX коммитят и пушат **в ветку своей задачи** сами: так запускается CI
  проекта, который входит в локальный гейт перед In Review (`tasktracker.md`).
- Сообщение коммита — тип и номер задачи, например `feat(Pre.Dev-12): …`.
- Merge в основную ветку, теги и деплой — только по просьбе владельца.
- Секреты, `.env` и персональные данные в коммит не попадают.

## Документация после реализации

Dev, QA и DevOps **не правят** карточки БФ и страницы компонентов: изменение поведения,
контракта, модели данных или окружения они описывают комментарием к задаче. Аналитик
приводит страницы к факту (`implemented`) и запускает
`python product_docs/check_product_docs.py` — Definition of Done слоя документации
(`product_docs.md`).

## Границы

- Требований агенты не придумывают и не меняют: владелец спецификации — аналитик.
- Решения, меняющие скоуп или срок, — рекомендация; финал за владельцем.
- Предупреждай, не блокируй: нехватку данных называй и продолжай с допущением, помеченным
  как допущение. Исключение — ворота выше: без них задачу не начинают.
- Файлы агентов — плоский Markdown без маркеров шаблонизатора; изменённые файлы агентов
  подхватываются только после перезапуска сессии.
