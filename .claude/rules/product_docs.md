# Живая документация продукта (`product_docs/`)

> Зеркало канона `.agents/rules/product_docs.md` для Claude Code; собирает `python scripts/sync_harness_mirrors.py`,
> вручную не правь — правка делается в каноне.

> Источник для: плоскостей документации, статусов бизнес-функции, результата проектирования,
> триггеров синхронизации и Definition of Done слоя 2. Другие файлы на эти темы ссылаются
> сюда. Версия: 2026-11-12.

Канон метода: `CLAUDE.md` → раздел «Живая документация продукта», `Rules.md` §3.4/§3.4.1,
`product_docs/README.md`.

Смысл: `output/` — журнал (события BABOK по времени + текст требований + граф 5.1), по нему
нельзя ответить «как продукт устроен сейчас». Рядом ведётся второй слой — `product_docs/`:
документация сохраняется **в четырёх плоскостях** сразу после утверждения аналитики.

## Четыре плоскости

| Плоскость | Папка | Что хранит | Кто пишет |
|---|---|---|---|
| Журнал и требования (слой 1) | `output/` | текст требований, граф 5.1, события BABOK | MCP-инструменты глав, аналитик |
| Бизнес-функции | `product_docs/01_business_functions/` | карточки БФ: требования по ID, UI, история изменений, перечень задач эпика | аналитик |
| Системные компоненты | `product_docs/02_system_components/` | паспорт (SRV), API, SEQ, таблицы (MAP), ERD, отказы (FLV) | аналитик; блок «Архитектурное решение» — архитектор |
| Архитектура | `architecture/` (если ведётся) | C4 (L1/L2), ADR, NFR-матрица, развёртывание | архитектор / агент Arch |

Реестр — `product_docs/INDEX.md`: БФ ↔ требования ↔ компоненты ↔ задачи ↔ релиз.
Текст требований живёт только в слое 1 (`output/data/<project_id>/specs/`);
`product_docs/` ссылается по ID и ничего не копирует. Страницы компонентов ссылаются
на `architecture/`, не дублируя её. Остальные области записи (дизайн, код, тесты,
инфраструктура) — `dev_team.md`.
Если `product_docs/` нет — предложи `python init_product_docs.py`, структуру вручную не создавай.

## Статусы БФ: `idea → planned → in_dev → implemented`

Статус меняет только аналитик.

| Статус | Смысл | Когда ставится |
|---|---|---|
| `idea` | требований в слое 1 ещё нет | при заведении карточки |
| `planned` | требования утверждены (5.5), решение описано, реализации нет; обязателен раздел «Планируемое изменение»; страница компонента разделяет «Сейчас» / «Планируется» | после Гейта 2 |
| `in_dev` | задачи разработки в работе | по сигналу Arch «разработка BF-NN начата» (`dev_team.md`) |
| `implemented` | реализовано, принято, страницы приведены к факту | после QA Pass и синхронизации слоя 2 |

## Результат проектирования

Физическая ERD, контракты API, sequence, маппинг живут на странице компонента
(`02_system_components/`); файл в `output/reports/` остаётся журнальной записью о выполненной
работе и не правится. Логическая ERD и словарь данных — требования, остаются в `output/`.

## Триггеры синхронизации (Rules.md §3.4.1)

«Синхронизируй документацию», «обнови product_docs», «создай карточку бизнес-функции»,
«создай страницу компонента», «проверь документацию продукта», «начни новую функцию».
Обязательно: **после 7.x, решения по CR (5.4) и пакета утверждения (5.5)** выполняй шаг
«синхронизировать product_docs» — обнови карточку БФ, страницу компонента, версию БФ
в «Истории изменений» и строку INDEX. То же — после QA Pass по задаче, меняющей поведение:
изменения Dev, QA и DevOps приходят комментариями к задаче.

## Definition of Done слоя 2

Задача, меняющая требования или поведение, не закрыта, пока:
(а) требование обновлено в слое 1 через CR/5.2; (б) обновлены карточка БФ и страница
компонента; (в) обновлена строка `INDEX.md`; (г) `python product_docs/check_product_docs.py`
выполняется без ошибок (`--fix` обновляет таблицы требований в карточках из графа 5.1).
Запускай проверку перед закрытием любой задачи, меняющей требования или поведение,
и после каждого пакета 5.5. Ошибки исправь, предупреждения назови аналитику.
Кто переводит такую задачу в Done — `tasktracker.md`.
`.puml` → `.svg` — `bash product_docs/render_diagrams.sh` (Docker); публичные сервисы
рендера не использовать.

## Развитие продукта — тот же `project_id`

Новые функции и следующие релизы ведутся в том же `project_id`; новый идентификатор
или экземпляр платформы для них не заводится — это разорвёт трассировку. Новый
бейзлайн (например, v2.0) создаётся по 5.5 после утверждения требований первой новой
функции, не заранее.

## Связанные правила

- Ворота Arch / Dev / QA, один писатель на область — `dev_team.md`.
- Задачи и эпики в трекере, связь задач с BF-NN — `tasktracker.md`.

Подробный метод и шаблоны: `product_docs/README.md` (карточка — `product_docs/_templates/bf_card.md`,
страница компонента — `_templates/component_page.md`).
