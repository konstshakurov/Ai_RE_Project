**Агент сам передвигает свою задачу в трекере по колонкам по мере работы** — это касается
всех ролей, включая DevOps. Ручное передвижение владельцем не предусмотрено; задача,
«зависшая» не в той колонке, — сбой агента.

## Колонки

Названия и состав колонок задаются при старте проекта; ниже — типовая схема на примере
YouGile. В других трекерах механика та же: в Linear это статусы, в Jira — переходы статусов.
Других названий колонок («В работе», «Готово», «На проверке QA») в правилах нет: если
трекер проекта называет колонки по-русски, это те же четыре колонки.

| Колонка | Когда |
|---|---|
| Backlog | задача в плане, работа не началась |
| In Progress | работа реально началась |
| In Review | работа завершена исполнителем, ждёт проверки |
| Done | критерии приёмки выполнены и приняты |

## Цикл задачи — кто и когда переносит

1. **Backlog → In Progress** — исполнитель, в момент, когда взял задачу и проверил ворота
   своей роли (ворота — `dev_team.md`). Сюда относится и первое чтение задачи, планов, кода.
2. **In Progress → In Review** — исполнитель, когда работа готова, локальный гейт проекта
   прошёл (линтеры, тесты, audit секретов — набор свой у каждого проекта) и описание задачи
   обновлено: что сделано, что осталось. Для Dev-задачи это сигнал QA-агенту.
3. **In Review → Done:**
   - задача, которую проверяет QA, — **QA после Pass**; апрув владельца не нужен (владелец
     принимает релиз на Гейте 4, `workflow_scheme.md`);
   - если задача меняет поведение, контракт API, модель данных или окружение — QA фиксирует
     Pass комментарием, а в Done задачу переводит **аналитик** после синхронизации слоя 2
     (DoD — `product_docs.md`);
   - задача без QA-проверки (RE, Arch, UX, DevOps, мелкие правки) — исполнитель после
     приёмки владельцем; для UX приёмка — это апрув `decision.md` (`ui_workflow.md`).
4. **Замечания QA** — QA возвращает проверяемую задачу в In Progress с перечнем замечаний
   по пунктам критериев; дефекты вне критериев заводит отдельными задачами с меткой `bug`.
5. **Внешняя блокировка** — исполнитель возвращает задачу в Backlog с короткой причиной в
   комментарии.

Не переносить в Done самовольно, если критерии приёмки не выполнены.

## Ограничения

- Одновременно **не более одной** задачи в In Progress на одного агента: владелец всегда
  видит, что «сейчас в работе».
- В In Review не больше 5 задач; выросшую очередь разобрать и вернуть реальное состояние.
- На переходе In Progress → In Review обновлять описание задачи — трекер отражает реальность.
- Стикеры, метки и приоритет не менять без поручения владельца (кроме метки `bug` у задач,
  которые заводит QA).
- Неблокирующие уточнения — комментарием в задаче, не сообщением владельцу.

## Названия задач

Единый формат для всех ролей и трекеров:

```
[BF-NN] Pre.<Роль>-N: <суть>
[BF-NN / CR-NNN] Pre.<Роль>-N: <суть>      — задачи CR-эпика
```

- Роли: `RE` (аналитик), `Arch`, `UX`, `Dev`, `QA`, `DevOps`; нумерация у каждой роли своя.
- `Pre.` — префикс задач этого проекта; в другом проекте он задаётся при подключении команды
  (`init_dev_team.py --task-prefix`).
- Задача без бизнес-функции (инфраструктура) — без `[BF-NN]`, в эпике «Инфраструктура/ops».
- Перед созданием задачи проверь список задач, чтобы не завести дубль.

## Содержимое задачи

Задача ссылается на `BF-NN`, ID требований (FR-041, UC-ROS, …) и страницы компонентов, а
не на файлы `output/reports/`. Обязательные поля задаёт Arch при декомпозиции (`arch.md`):
роль, зависимости, вход, выход, критерии приёмки, срок.

## Эпики: задачи ↔ бизнес-функции

1. **Эпик = бизнес-функция.** Когда БФ проходит Гейт 2 (пакет 5.5 принят, карточка BF-NN в
   `planned`), создаётся задача-эпик «BF-NN: <название>». Все задачи функции (RE, Arch, UX,
   Dev, QA, DevOps, системный анализ и интеграции) — подзадачи этого эпика.
2. **До появления БФ.** Работы аналитика ведутся в эпиках аналитики: стартовая фаза проекта —
   «Аналитика: <объём>», новая функция в живом проекте — эпик «BF-NN: аналитика»
   (создаётся раньше карточки). Работы без БФ — эпик «Инфраструктура/ops».
3. **Связи.** Перечень задач эпика хранится в карточке BF-NN; обновляет его **аналитик** при
   синхронизации слоя 2. Arch создаёт задачи в трекере, но карточку не правит.
4. **Движение эпика.** `In Progress` — при старте первой подзадачи; `Done` — когда все
   подзадачи в Done и DoD слоя 2 закрыт. Эпик переносит аналитик.
5. **CR внутри эпика.** CR, открытый до закрытия эпика, ведётся в том же эпике; эпик не
   переводится в Done, пока задачи CR не закрыты.
6. **CR после Done.** Для реализованной БФ новые CR оформляются новым эпиком
   «BF-NN (CR-NNN)» (крупное изменение — «BF-NN v2»); цепочка RE → Arch → … → QA
   повторяется; документация ведётся в той же карточке BF-NN, версии растут.
7. **Другой трекер.** Эпик — это эпик, фича или milestone со связанными задачами; механика
   та же.

## Как (пример — MCP yougile)

- Прочитать: `tools.yougile.get_task_data({ id: "<id задачи>", cursor: "" })`.
- Перенести или обновить: `tools.yougile.manage_tasks({ tasks: [{ id, title: null,
  columnId, description: null, color: "primary", complete: null, archived: null }] })`.
  Поле `color` обязательно даже при простом переносе.
- Комментарий (причина блокировки, замечания, Pass): `tools.yougile.send_chat_message`.
