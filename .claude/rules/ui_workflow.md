# UX-воркфлоу: изменения интерфейса идут через согласование

> Зеркало канона `.agents/rules/ui_workflow.md` для Claude Code; собирает `python scripts/sync_harness_mirrors.py`,
> вручную не правь — правка делается в каноне.

> Источник для: UI-цикла, ворот Dev для UI-задач и приёмки UI. Версия: 2026-11-12.

Правило владельца: **любые задачи и изменения в UI согласуются с владельцем до
реализации.** Правило наследуют все агенты разработки.

## Цепочка

```
Аналитик (спецификация) → Arch (декомпозиция) → UX (варианты) → [апрув владельца] → Dev → QA
```

1. **Arch** раскладывает спецификацию на задачи по ролям, включая `Pre.UX-N`. Каждая задача
   с видимым изменением интерфейса получает пару: `Pre.UX-N` → `Pre.Dev-N`, где Dev зависит
   от UX. Чисто серверные задачи UX не требуют.
2. **UX** проектирует 2-3 варианта (прототипы в `design/<задача>/`), готовит рекомендацию.
3. **Владелец** выбирает вариант или даёт правки (Гейт 3). До явного апрува Dev не стартует.
4. **UX** фиксирует `design/<задача>/decision.md` со статусом `approved` и комментарием в
   трекере. Только это — вход для Dev.
5. **Dev** реализует по `decision.md`. Отклонение от решения — только через возврат к UX.
6. **QA** проверяет UI против критериев приёмки из `decision.md`.

## Что считается изменением UI

Новый или изменённый экран, компонент, поток, расположение элементов, тексты интерфейса,
состояния (пусто/ошибка/загрузка), стили и токены. Не считается: исправление ошибки без
видимого изменения, рефакторинг, серверная логика.

## Приёмка реализации

Реализацию UI по утверждённому `decision.md` принимает **QA-агент**; апрув владельца на
реализацию не требуется. Владельцу апрув нужен на дизайн (шаг 3) и на изменение скоупа.

1. Dev завершает задачу и переводит её в In Review (`tasktracker.md`).
2. QA сверяет стенд с критериями приёмки из `decision.md` и макетом: ключевые экраны,
   темы и ширины, заданные в решении; результат — в `qa/` и комментарием в трекере
   (Pass / замечания по пунктам критериев).
3. Pass → Done по правилам `tasktracker.md`. Владельцу приходит короткая сводка, а не запрос
   на проверку.

Кому идёт находка QA:

| Находка | Куда |
|---|---|
| Реализация расходится с `decision.md` или макетом | замечание на Dev-задачу (`tasktracker.md`), не владельцу |
| У UI-задачи нет `decision.md` в статусе `approved` — нарушение процесса | владельцу |
| Макет расходится с требованиями | CR аналитику (5.4) |
| Вопрос вкуса, который критерии приёмки не закрывают | владельцу |

## Ворота для Dev

Задача с изменением UI без `design/<задача>/decision.md` со статусом `approved` — **не
реализуется**. Dev называет причину, сообщает номер ожидаемой UX-задачи и ничего не пишет
в каталог фронтенда. Исключение — только прямое указание владельца в чате. Остальные ворота
Dev — `dev_team.md`.

## Кто что пишет

| Область | Писатель |
|---|---|
| `design/` | только `ux` |
| каталог фронтенда | только `dev` (по `decision.md`) |
| скиллы платформы (`skills/`, шаблоны `templates/`, `.claude/skills/`) | владелец платформы; агенты читают |

## Границы

- UX не меняет требований; пробел или противоречие — через аналитика (CR, 5.4).
- Решения, меняющие скоуп или срок, — рекомендация; финал за владельцем.
- Предупреждай, не блокируй: если UX-согласование задерживает критический путь, назови
  это владельцу и предложи вариант («один вариант + как сейчас» для точечной правки).
