# Rules.md — правила продуктового проекта

Один экземпляр Ai_RE_Project ведёт **один** продуктовый проект (без вложенной
структуры «эпик → проекты», в отличие от предыдущей платформы). Все правила
ниже относятся к этому единственному проекту.

Эти правила будут меняться и дополняться по ходу использования платформы —
это рабочий документ, а не зафиксированная раз и навсегда методика.

## 1. Компетенции и с чего начинать

Ai_RE_Project покрывает три компетенции аналитика — определяй нужную по
формулировке запроса пользователя, полный алгоритм выбора и триггеры описаны
в `CLAUDE.md`:

| Компетенция | Когда | Скилл |
|---|---|---|
| 1. Оценка этапа аналитики | Контракт на разработку ещё не заключён, нужно оценить трудозатраты/сроки | `skills/analyst_estimate/SKILL.md` |
| 2. Аналитика на продуктовом проекте (БА + СА, фуллстек-аналитик) | Контракт заключён, команда собрана, идёт работа над требованиями | Главы BABOK 3–7, `skills/planning_prep/SKILL.md` и далее |
| 3. Предпроект | Контракт заключён только на предпроектный технический этап | `skills/analyst_pre_project/SKILL.md` |

Приоритет разграничения компетенций 1/2/3 — см. `CLAUDE.md`, раздел «Как
определить с чего начать».

## 2. Структура проекта

```
input/        ← входные материалы клиента/проекта, включая оценку с presale
output/       ← результаты Компетенции 2 (главы BABOK) и Компетенции 3 (предпроект)
estimate/     ← результаты Компетенции 1 — оценки, сделанные ПОСЛЕ старта продуктового проекта
product_docs/ ← живая документация продукта (бизнес-функции, системные компоненты); создаётся
                `python init_product_docs.py` из `templates/product_docs/`
skills/       ← все скиллы платформы
```

## 3. Входные и выходные данные

**3.1.** Все входящие материалы — транскрипты интервью, воркшопов, бизнес-правила,
регламенты, техспеки, оценка с presale и т.д. — сохраняются в `input/` и
считаются контекстом проекта.

**3.1.1. Триггеры:** входные данные, информация от клиента, запись созвона,
сохрани документы клиента.

**3.2.** Все созданные результаты работы по Компетенции 2 (главы BABOK) и
Компетенции 3 (предпроект) сохраняются в `output/`:
- `output/data/` — JSON, машиночитаемые данные для MCP-инструментов
- `output/reports/` — Markdown-отчёты для людей
- `output/specs/` — спеки 7.1 и другие артефакты системного анализа

Структура `output/` может донастраиваться самим специалистом под конкретный
проект (например, иерархия по модулям системы вместо плоского списка) — это
не меняет правило «результаты Компетенции 2/3 живут в output/».

**3.2.1. Триггеры:** создай концепцию, создай оценку, создай план работ,
создай требования, создай описание системы, создай описание архитектуры,
создай перечень фич, создай User Story, создай Use Case.

Полный пакет архитектурных артефактов (C4, ARC42, TOGAF) по триггеру «создай
описание архитектуры» и аналогичным — `skills/analyst_it_architecture/SKILL.md`.
Работает только в Компетенции 2 и приоритетно как задача Архитектора
проекта, а не аналитика по умолчанию (аналитик берёт её на себя только при
отсутствии архитектора/разработчика в команде или по решению команды) — см.
`CLAUDE.md`, раздел «Дополнительные скиллы».

**3.2.2.** При обновлении или внесении изменений в уже существующий документ
(концепция, оценка и т.д.) — запрашивать: «Обновить существующий или создать
новый документ?». При ответе «создать новый» — сохранить новый файл со
следующим порядковым номером (например, `concept_v2.md`).

**3.3.** Все результаты работы по Компетенции 1 (`skills/analyst_estimate`),
выполненной уже ПОСЛЕ старта продуктового проекта (переоценка), сохраняются в
`estimate/` (`concept.md`, `estimate.md`, `estimate_v2.md` и т.д. — правило
версионирования 3.2.2 действует и здесь).

**3.4. Живая документация (`product_docs/`).** `output/` — журнал и единственный источник
текста требований; `product_docs/` — слой «как продукт устроен сейчас»: карточки
бизнес-функций (`BF-NN`) и страницы системных компонентов, со ссылками на требования по ID
(текст не копируется).

| Слой | Папка | Что хранит | Кто пишет |
|---|---|---|---|
| Журнал и требования | `output/` | текст требований, граф 5.1, события BABOK | MCP-инструменты глав, аналитик |
| Бизнес-функции | `product_docs/01_business_functions/` | карточки БФ: требования по ID, UI, история изменений | аналитик |
| Системные компоненты | `product_docs/02_system_components/` | паспорт, API, диаграммы (SEQ), таблицы и ERD, отказы (FLV) | аналитик; блок «Архитектурное решение» — архитектор |
| Архитектура | `architecture/` (если ведётся) | C4, ADR, нагрузка, развёртывание | архитектор или агент Arch |

Правила:
- результат проектирования (физическая ERD, API, sequence, маппинг) хранится на странице
  компонента, а не только в `output/reports/`; логическая ERD и словарь данных остаются
  требованиями в `output/`;
- после 7.x, решения по CR (5.4) и пакета утверждения (5.5) аналитик синхронизирует
  `product_docs/` и запускает `python product_docs/check_product_docs.py` без ошибок
  (Definition of Done);
- развитие продукта (новые функции, следующие релизы) ведётся в том же `project_id`; новый
  бейзлайн (например, v2.0) создаётся после утверждения требований первой новой функции;
- передача архитектору — по формальному сигналу готовности (карточка `planned` + бейзлайн +
  запись в трекере); один писатель на область.
Подробно — `product_docs/README.md` (шаблон: `templates/product_docs/README.md`).

**3.4.1. Триггеры:** синхронизируй документацию, обнови product_docs, создай карточку бизнес-функции,
создай страницу компонента, проверь документацию продукта, начни новую функцию.

## 4. Определение состава артефактов продуктового проекта

Состав артефактов, которые нужно разработать на продуктовом проекте,
определяется одним из трёх способов:

**а)** Составом артефактов из оценки, сделанной по `skills/analyst_estimate`
на этапе presale и вложенной в `input/` вручную специалистом (или по запросу
от агента на старте проекта).

**б)** Если оценки от presale нет — на усмотрение аналитика/команды и LLM,
исходя из материалов, вложенных в `input/`.

**в)** Если при старте продуктового проекта нужна переоценка со стороны
аналитика:
- применить `skills/analyst_estimate`;
- сохранить `concept.md`, `estimate_pp.md` (или аналогичные) в `estimate/`
  (см. правило 3.3);
- определить состав артефактов из новой оценки.

## 5. Изоляция контекста

Один экземпляр платформы = один продуктовый проект = один контекст. Если
нужно вести несколько продуктовых проектов параллельно — разворачивай
отдельный экземпляр Ai_RE_Project на каждый (см. `README.md`, раздел
«Установка»), а не смешивай их материалы в одном `input/`/`output/`.

## 6. Инструментарий

Все скиллы в `skills/` доступны в рамках одного продуктового проекта без
разделения на «эпик» и «инструментарий» — это плоская структура одного
проекта.

## 7. Инструмент OpenSpec

OpenSpec (создание документации и декомпозиция на задачи для агентской
разработки) используется в проекте **только при дополнительном подтверждении
пользователя**. По умолчанию работает Ai_RE_Project, а не OpenSpec — не
запускай и не предлагай OpenSpec как шаг по умолчанию, даже если задача
похожа на спецификацию/декомпозицию.

## 8. Никогда не удаляй данные

Депрецированные требования помечаются через `deprecate_requirements` (5.2),
но не удаляются — история должна сохраняться. При попытке удалить данные
проекта — предупреди пользователя и предложи депрекацию вместо удаления.

## 9. Команда разработки (опционально)

Агентов разработки (`arch`, `ux`, `dev`, `qa`, `devops`) платформа не включает по умолчанию:
они подключаются только если пользователь ведёт разработку помимо аналитики —
`python init_dev_team.py --project-id <project_id> …` (шаблон — `templates/dev_team/`).
Цепочка: аналитик → Arch → UX → апрув владельца → Dev → QA; вход для Arch — карточка БФ
`planned` и утверждённые требования (п. 3.4); один писатель на область; Dev, QA и DevOps
документацию продукта не правят, а сообщают об изменениях комментарием к задаче.

**9.1. Триггеры:** подключи команду разработки, нужны агенты разработки, добавь архитектора и
разработчиков.
