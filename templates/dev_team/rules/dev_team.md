# Команда разработки проекта {{PROJECT_TITLE}}

> Источник для: состава ролей и областей записи, ворот Arch / Dev / QA, коммитов, владения
> миграциями БД и статусом `in_dev`. Цикл задачи в {{TRACKER}}, названия задач и эпики —
> `.claude/rules/tasktracker.md`; UI-цикл — `.claude/rules/ui_workflow.md`.

Опциональный слой: агенты `arch`, `ux`, `dev`, `qa`, `devops` в `.claude/agents/` (установлен
`python init_dev_team.py`). Он не входит в четвёрку платформенных агентов
(`analyst`, `orchestrator`, `worker_llm`, `worker_file`) и не меняет их работу: без него платформа
ведёт только аналитику.

## Роли и области — один писатель на область

| Агент | Задачи | Пишет только в |
|---|---|---|
| аналитик (ведущая сессия) | `{{TASK_PREFIX}}RE-N` | `output/` (через MCP-инструменты), `product_docs/`, в том числе статус карточки БФ |
| `arch` | `{{TASK_PREFIX}}Arch-N` | `architecture/`; блок «Архитектурное решение» страниц компонентов; задачи в {{TRACKER}} |
| `ux` | `{{TASK_PREFIX}}UX-N` | `design/` |
| `dev` | `{{TASK_PREFIX}}Dev-N` | `{{BACKEND_DIR}}`, `{{FRONTEND_DIR}}`, тесты к коду; `{{MIGRATIONS_DIR}}` — только в задаче на изменение схемы |
| `qa` | `{{TASK_PREFIX}}QA-N` | `{{TESTS_DIR}}`, `qa/` |
| `devops` | `{{TASK_PREFIX}}DevOps-N` | compose-файлы, Dockerfile, `infra/`, `scripts/`, CI, `.env.example` |

- Параллельные задачи в одну область не заводятся. Агент сообщает, если смежная задача в
  работе, и не правит те же файлы.
- Пробел или противоречие в требованиях исполнитель не правит сам — заводит Issue или CR
  (5.4) аналитику.

## Цепочка

```
Аналитик (требования, карточка БФ planned)
  → Arch (архитектура, декомпозиция на задачи)
  → UX (варианты) → [апрув {{OWNER}}]   — только для задач с изменением UI
  → Dev → QA
```

DevOps подключается по задачам окружения, сборки и деплоя. Задача с изменением интерфейса идёт
через `ux`; серверные и инфраструктурные задачи его пропускают.

## Ворота

**Arch** берёт функцию в работу, только если выполнено всё:

1. карточка `product_docs/01_business_functions/BF-NN_*/README.md` в статусе `planned` с
   заполненным разделом «Планируемое изменение»;
2. требования, на которые она ссылается, утверждены (пакет утверждения 5.5);
3. аналитик подал сигнал в {{TRACKER}}: «аналитика по BF-NN завершена» со ссылками на
   карточку и пакет.

**Dev и QA** берут задачу, только если:

1. карточка БФ в статусе `planned` или `in_dev`;
2. задача создана Arch и содержит вход, выход и критерии приёмки;
3. для задачи с изменением UI — есть `design/<задача>/decision.md` со статусом `approved`.

Ворота не пройдены — назови, чего не хватает, верни задачу и ничего не делай в чужой области.
Если роль играет живой человек, правило то же.

## Статус бизнес-функции `in_dev`

Карточку БФ пишет только аналитик, статус тоже. Arch при старте разработки (первая
подзадача Dev ушла в работу) пишет в эпик сигнал «разработка BF-NN начата»; аналитик по
этому сигналу переводит карточку в `in_dev`.

## Миграции БД

Схему меняет Dev в отдельной задаче `{{TASK_PREFIX}}Dev-N` на изменение схемы; Arch согласует
изменение схемы до реализации. В других задачах Dev `{{MIGRATIONS_DIR}}` не трогает. DevOps
миграции не пишет, а применяет их при деплое (с предварительным дампом БД).

## Коммиты

- Dev, QA, DevOps и UX коммитят и пушат **в ветку своей задачи** сами: так запускается CI
  проекта, который входит в проверку перед переводом задачи на проверку.
- Сообщение коммита — тип и номер задачи, например `feat({{TASK_PREFIX}}Dev-12): …`.
- Merge в основную ветку, теги и деплой — только по просьбе {{OWNER}}.
- Секреты, `.env` и персональные данные в коммит не попадают.

## Документация после реализации

Dev, QA и DevOps **не правят** карточки БФ и страницы компонентов: изменение поведения,
контракта, модели данных или окружения они описывают комментарием к задаче. Аналитик приводит
страницы к факту (`implemented`) и запускает `python product_docs/check_product_docs.py` —
Definition of Done слоя документации (`product_docs/README.md`).

## Границы

- Требований агенты не придумывают и не меняют: владелец спецификации — аналитик.
- Решения, меняющие скоуп или срок, — рекомендация; финал за {{OWNER}}.
- Предупреждай, не блокируй: нехватку данных называй и продолжай с допущением. Ворота
  выше — исключение: без них задачу не начинают.
- Файлы агентов — плоский Markdown без маркеров шаблонизатора; изменённые файлы агентов
  подхватываются только после перезапуска сессии (`/exit`, затем `claude --continue`).
