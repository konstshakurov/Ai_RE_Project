# UX-воркфлоу: изменения интерфейса идут через согласование

Правило {{OWNER}}: **любые задачи и изменения в UI согласуются до реализации.** Правило
наследуют все агенты разработки.

## Цепочка

```
Аналитик (требования, карточка БФ) → Arch (декомпозиция) → UX (варианты) → [апрув {{OWNER}}] → Dev → QA
```

1. **Arch** раскладывает функцию на задачи по ролям, включая `{{TASK_PREFIX}}UX-N`. Каждая
   задача с видимым изменением интерфейса получает пару `{{TASK_PREFIX}}UX-N` →
   `{{TASK_PREFIX}}Dev-N`, где Dev зависит от UX. Чисто серверные задачи UX не требуют.
2. **UX** проектирует 2-3 варианта (прототипы в `design/<задача>/`), готовит рекомендацию.
3. **{{OWNER}}** выбирает вариант или даёт правки. До явного апрува Dev не стартует.
4. **UX** фиксирует `design/<задача>/decision.md` со статусом `approved` и комментарием в
   {{TRACKER}}. Только это — вход для Dev.
5. **Dev** реализует по `decision.md`. Отклонение от решения — только через возврат к UX.
6. **QA** проверяет UI против критериев приёмки из `decision.md`.

## Что считается изменением UI

Новый или изменённый экран, компонент, поток, расположение элементов, тексты интерфейса,
состояния (пусто/ошибка/загрузка), стили и токены. Не считается: исправление ошибки без
видимого изменения, рефакторинг, серверная логика.

## Приёмка реализации

Реализацию UI по утверждённому `decision.md` принимает **QA-агент**; апрув {{OWNER}} на
реализацию не требуется. {{OWNER}} нужен апрув на дизайн (шаг 3) и на изменение скоупа.

1. Dev завершает задачу и переводит её в «На проверке QA» (код не коммитится без запроса).
2. QA сверяет стенд с критериями приёмки из `decision.md` и макетом: ключевые экраны, темы и
   ширины, заданные в решении; результат — в `qa/` и комментарием в {{TRACKER}} (Pass /
   замечания по пунктам критериев). Расхождения QA заводит багами на Dev-задачу, а не владельцу.
3. Pass → задача «Готово». {{OWNER}} приходит короткая сводка, а не запрос на проверку.

К {{OWNER}} возвращаются: изменение дизайна или скоупа, расхождение макета и требований (CR
аналитику, 5.4), вопрос вкуса, который критерии приёмки не закрывают.

## Ворота для Dev

Задача с изменением UI без `design/<задача>/decision.md` со статусом `approved` — **не
реализуется**. Dev называет причину, сообщает номер ожидаемой UX-задачи и ничего не пишет в
`{{FRONTEND_DIR}}`. Исключение — только прямое указание {{OWNER}} в чате.

## Кто что пишет

| Область | Писатель |
|---|---|
| `design/` | только `ux` |
| `{{FRONTEND_DIR}}` | только `dev` (по `decision.md`) |
| `.claude/skills/` | владелец платформы агентов; агенты читают |

## Границы

- UX не меняет требований; пробел или противоречие — через аналитика (CR, 5.4).
- Решения, меняющие скоуп или срок, — рекомендация; финал за {{OWNER}}.
- Предупреждай, не блокируй: если UX-согласование задерживает критический путь, назови это
  {{OWNER}} и предложи вариант («один вариант + как сейчас» для точечной правки).
