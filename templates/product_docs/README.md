# product_docs — живая документация продукта

Назначение: ОДНО место, где видно, **как продукт устроен сейчас** — по бизнес-функциям, системным компонентам и архитектуре — с трассировкой к требованиям BABOK, задачам и коду. Каркас создан платформой Ai_RE_Project командой `python init_product_docs.py`; эта папка принадлежит продуктовому проекту и дальше развивается вместе с ним.

## Зачем два слоя

`output/` — журнал: файлы-события BABOK по времени и требования по типам (`fr_`, `uc_`, `br_`…). Он незаменим для аудита и трассировки, но по нему трудно ответить на вопрос «как сейчас работает функция N?» — ответ разбросан по десяткам файлов, а утверждённые тексты со временем отстают от реализации. Поэтому рядом ведётся второй слой.

```
СЛОЙ 1 — ЖУРНАЛ (output/)                         СЛОЙ 2 — ЖИВАЯ ДОКУМЕНТАЦИЯ (product_docs/)
output/data/<project_id>/…  JSON + specs/ (MCP)    «как устроено сейчас», по функциям и компонентам
output/reports/<project_id>/…  события BABOK       ссылается на ID требований, текст не копирует
  → история, аудит, граф трассировки 5.1             → точка входа для человека и агентов
```

| Слой | Папка | Что хранит | Кто пишет |
|---|---|---|---|
| Журнал и требования | `output/` | текст требований, граф 5.1, события BABOK | MCP-инструменты глав, аналитик |
| Бизнес-функции | `product_docs/01_business_functions/` | карточки БФ: требования по ID, UI, история изменений | аналитик |
| Системные компоненты | `product_docs/02_system_components/` | паспорт, API, диаграммы (SEQ), таблицы и ERD, отказы (FLV) | аналитик; блок «Архитектурное решение» — архитектор |
| Архитектура | `architecture/` (если ведётся) | C4, ADR, нагрузка, развёртывание | архитектор или агент Arch |

Требование живёт ровно в одном месте — в `output/data/<project_id>/specs/`; правится через 5.2 `update_requirement` и CR 5.4. В слое 2 на него ссылаются по ID.

**Новый `project_id` для следующего релиза не заводится.** `project_id` — ключ графа трассировки и бейзлайна; второй идентификатор разорвёт связи между уже утверждёнными требованиями и новыми. Развитие продукта (новые функции, следующие релизы после первой поставки) — те же `project_id` и граф: поле «Релиз» в карточке БФ, метка в трекере; новый бейзлайн (например, v2.0) создаётся по 5.5 после утверждения требований первой новой функции.

## Структура

```
product_docs/
  README.md                метод и правила (этот файл)
  INDEX.md                 реестр: БФ ↔ требования ↔ компоненты ↔ задачи ↔ релиз
  _templates/              bf_card.md, component_page.md
  01_business_functions/   BF-NN_<имя>/README.md — шапка бизнес-функции
  02_system_components/    <компонент>/           — SRV/API/SEQ/MAP/ERD/FLV
  check_product_docs.py    проверка актуальности
  render_diagrams.sh       рендер PlantUML (нужен Docker)
```

Префиксы файлов компонента: `SRV` — паспорт (`README.md`), `API` — контракты, `SEQ` — диаграммы последовательности (`seq/*.puml`), `MAP` — таблицы и справочники, `ERD` — модель данных, `FLV` — отказы и деградация, `MON` — мониторинг.

## Где хранится ERD и модель данных

| Что | Слой | Где |
|---|---|---|
| Логическая ERD и словарь данных — требования | 1 | `output/data/<project_id>/specs/erd_*`; в карточках БФ — ссылка |
| Физическая модель, ER-диаграмма, таблицы, DDL — техническое решение | 2 | `02_system_components/<база>/`: `README.md` (SRV, миграции), `MAP_tables.md`, `ERD_*.md` |
| Первоисточник схемы | код | миграции проекта — страница объясняет схему, DDL не дублирует |

Общее правило: **результат проектирования (ERD, API, sequence) живёт на странице компонента; журнал хранит факт, что работа выполнена.** Файл-отчёт в `output/reports/` остаётся записью о задаче и не правится, актуализируется страница компонента.

## Жизненный цикл: `idea` → `planned` → `in_dev` → `implemented`

| Статус | Смысл | Кто ставит |
|---|---|---|
| `idea` | требований в слое 1 ещё нет | аналитик |
| `planned` | требования утверждены (5.5), решение описано, реализации нет | аналитик — карточка БФ; архитектор — целевые страницы компонентов |
| `in_dev` | задачи в работе | архитектор / TL при декомпозиции |
| `implemented` | реализовано, принято, страницы приведены к факту | аналитик (после DoD) |

В карточке `planned` обязателен раздел **«Планируемое изменение»**: что добавляется и что меняется (по ID требований), какие компоненты и контракты затрагиваются, ссылка на дизайн (если есть интерфейс), открытые вопросы. Страница компонента в состоянии `planned` разделяет «Сейчас» и «Планируется».

## Сценарий новой бизнес-функции

Вход для архитектора и разработки — **два источника**: (1) утверждённые требования-дельта в слое 1 (5.4/5.5) — что менять; (2) карточка БФ, страницы компонентов, `architecture/`, код — где менять и что уже есть. Задача в трекере ссылается на `BF-NN`, ID требований и страницы компонентов, а не на файлы `output/reports/`.

```
Аналитик (BABOK: требования в output/, 5.5)
  → карточка БФ: planned + версия + «Планируемое изменение»
  → сигнал готовности
  → архитектор (агент или человек): декомпозиция в трекере; целевые страницы (planned); ADR
  → UX → апрув владельца (если есть интерфейс)
  → разработка → тестирование
  → страницы implemented, INDEX обновлён
```

**Ворота:** архитектор не берёт задачу без карточки БФ `planned` с утверждёнными требованиями; он называет причину и возвращает задачу аналитику.

## Передача между ролями (агент или человек)

Порядок одинаков, кто бы ни принимал работу: если архитектор или TL — человек, он выполняет функции агента Arch, включая декомпозицию в трекере.

**Сигнал готовности аналитики — формальный** (сообщение в чате не оставляет следа для других ролей и агентов): (1) карточка БФ в статусе `planned` с версией и разделом «Планируемое изменение»; (2) бейзлайн утверждён по 5.5 (ссылка на пакет утверждения); (3) комментарий или задача в трекере «аналитика по BF-NN завершена» со ссылками на карточку и пакет.

**Один писатель на область:**

| Область | Пишет |
|---|---|
| `output/`, `01_business_functions/` | только аналитик |
| `02_system_components/` — контракты и диаграммы «как есть» | аналитик |
| блок «Архитектурное решение» страниц компонентов, `architecture/` | архитектор |
| дизайн, код, тесты | UX, разработка, тестирование |

Пробел или противоречие в требованиях архитектор не правит сам — заводит Issue или CR (5.4) аналитику. Замечания к карточке — комментарием в трекере; аналитик отвечает 5.2 или CR и меняет версию карточки. Решения, меняющие скоуп или срок, принимает владелец продукта. Разграничение прав на папки можно закрепить `CODEOWNERS`, если проект работает через pull request с защитой ветки (по умолчанию не используется).

## Definition of Done: «слой 2 обновлён»

Задача, которая меняет требования или поведение, не закрыта, пока: (а) требование обновлено в слое 1 через CR/5.2; (б) обновлены карточка БФ и страница компонента; (в) обновлена строка в `INDEX.md`; (г) `python product_docs/check_product_docs.py` выполняется без ошибок. Запускайте проверку и после каждого пакета утверждения 5.5.

## Проверка и рендер диаграмм

```bash
python product_docs/check_product_docs.py          # проверка
python product_docs/check_product_docs.py --fix    # обновить таблицы требований в карточках из графа 5.1
bash product_docs/render_diagrams.sh               # .puml -> .svg через образ plantuml/plantuml (нужен Docker)
```

**Ошибки** (код возврата 1): ID нет в графе; версия или статус в карточке не совпадают с графом; битые ссылки; БФ есть в INDEX без карточки или наоборот; `planned` без «Планируемого изменения»; неизвестный статус. **Предупреждения:** требование не покрыто ни одной БФ (кроме строки «Сквозные:» в INDEX); требования в `under_change`; компонент без БФ; БФ `implemented` без компонента; `.puml` без свежего `.svg`. Публичные сервисы для рендера диаграмм не использовать: имена систем и полей не должны уходить наружу.

Особенность Windows: двоеточие в заголовке (`title`) при регистрации диаграммы в графе превращает хвост имени файла в альтернативный поток NTFS — в названиях диаграмм двоеточие не использовать.

## Как начать

1. Создать карточки БФ по `_templates/bf_card.md` в `01_business_functions/BF-NN_<имя>/README.md` (ссылки на требования по ID, `--fix` заполнит названия и версии).
2. Описывать компоненты по риску: `_templates/component_page.md` в `02_system_components/<компонент>/`.
3. Занести БФ и компоненты в `INDEX.md`; запустить проверку.
4. По скиллам системного анализа (БД, REST API, UML Sequence, архитектура): регистрировать результат в графе 5.1 как раньше, а исходники класть на страницу компонента.
